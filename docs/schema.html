1. Overview

L5 is an embedded audit-trail storage engine. Each key (called a world) is a separate SQLite database containing an append-only HMAC chain and a content-addressable body store. The engine exposes five verbs: read, replace, append, delete, subscribe. Protocol adapters (HTTP, CoAP, MQTT, SSE) map onto these verbs; the engine knows nothing about protocols.

Everything below describes the on-disk format and the invariants the engine enforces. If you can read a SQLite file, you can verify the chain yourself without the engine binary.

2. Per-world SQLite schema

Each world is one directory containing universe.db. The database has these tables:

CREATE TABLE world_format(
    id      INTEGER PRIMARY KEY CHECK(id=1),
    version INTEGER NOT NULL CHECK(typeof(version)='integer') CHECK(version=2)
);

CREATE TABLE stage_meta(
    id          INTEGER PRIMARY KEY CHECK(id=1),
    generation  TEXT NOT NULL,               -- 32 lowercase hex, unique per incarnation
    body        BLOB DEFAULT x'',
    content_type TEXT DEFAULT 'application/octet-stream'
);

CREATE TABLE events(
    id           INTEGER PRIMARY KEY AUTOINCREMENT,  -- TimelineSeq
    timestamp    TEXT NOT NULL,                       -- UTC ms, e.g. 2026-06-30T12:00:00.000Z
    event_type   TEXT NOT NULL,                       -- put | append | delete_intent | delete_commit | delete_commit_failed | format
    target       TEXT DEFAULT '',                     -- world path
    body_sha256  TEXT DEFAULT '',                     -- 64 hex, points into cas_bodies
    size         INTEGER DEFAULT 0,                   -- body byte count
    content_type TEXT DEFAULT '',                     -- MIME type
    meta_sha256  TEXT DEFAULT '',                     -- 64 hex, SHA256 of canonical metadata
    hmac         TEXT NOT NULL,                       -- 64 hex, this row's HMAC
    prev_hmac    TEXT DEFAULT ''                      -- 64 hex, previous row's HMAC (empty for genesis)
);

CREATE TABLE event_headers(
    event_id INTEGER NOT NULL,
    name     TEXT NOT NULL,
    value    TEXT NOT NULL
);

CREATE TABLE cas_bodies(
    body_sha256 TEXT NOT NULL PRIMARY KEY
        CHECK(typeof(body_sha256)='text')
        CHECK(length(body_sha256)=64)
        CHECK(body_sha256 NOT GLOB '*[^0-9a-f]*'),
    body        BLOB NOT NULL CHECK(typeof(body)='blob')
) WITHOUT ROWID;

CREATE TABLE cas_state(
    id                  INTEGER PRIMARY KEY CHECK(id=1),
    first_retained_seq  INTEGER
        CHECK(first_retained_seq IS NULL OR
              (typeof(first_retained_seq)='integer' AND first_retained_seq > 0))
                              -- NULL = retain all; positive = prune before this seq
);

CREATE TABLE meta_headers(
    name  TEXT NOT NULL,
    value TEXT NOT NULL,
    PRIMARY KEY(name)
);

The world generation is stored once in stage_meta.generation. It is signed into every event HMAC, but it is not an events column.

3. HMAC chain

Every row in the events table carries an HMAC computed over 10 fields in fixed order. Each row's prev_hmac is the previous row's hmac. The first row (always format) has prev_hmac = "".

Row 1 (format)
prev_hmac: ""
type: format
hmac: 3a7f...c2
→
Row 2 (put)
prev_hmac: 3a7f...c2
body: "hello"
hmac: 8b21...e5
→
Row 3 (put)
prev_hmac: 8b21...e5
body: "updated"
hmac: d4e9...a1
→
Row N ...
prev_hmac: d4e9...a1

Change any signed field → recomputation fails. Break a link → the next row's prev_hmac does not match. Delete or insert a row → the verified walk fails. Without the HMAC key, a valid chain cannot be forged.

HMAC computation — 10 fields

hmac = HMAC-SHA256(key,
    prev         \0 len \0 <prev row hmac hex>  \0
    world        \0 len \0 home/note             \0
    timestamp    \0 len \0 2026-06-30T12:00:00.000Z \0
    type         \0 len \0 put                    \0
    target       \0 len \0 home/note             \0
    gen          \0 len \0 0a1b2c3d...ef         \0
    body-sha256  \0 len \0 e3b0c442...8e         \0
    size         \0 len \0 42                    \0
    content-type \0 len \0 text/plain            \0
    meta-sha256  \0 len \0 a1b2c3d4...f0         \0
)

Each field uses length-prefix framing (see next section). The key is the HMAC secret, typically from AUDITEDB_KEY environment variable. It never touches disk.

4. Length-prefix framing

Both HMAC and meta_sha256 use the same framing for every field:

label
\0
byte_len
\0
value
\0

Example: field type with value put:

type
\0
3
\0
put
\0

The length is the UTF-8 byte count of the value, not the character count. For ASCII they are equal; for multibyte characters (CJK, emoji) they differ. Both the Rust engine and the Python verifier use byte length.

Length-prefix framing makes adjacent fields unambiguous: value="a\0b" and value="a" + next_label="b" would produce the same byte sequence without framing. Format v2; see sha256_field in audit.rs.

5. meta_sha256

The meta_sha256 column is a SHA-256 hash of the event's metadata (content type + any custom headers). Headers are lowercased and sorted alphabetically before hashing.

meta_sha256 = SHA256(
    content-type  \0  10  \0  text/plain  \0
    header-name   \0  8   \0  x-custom    \0
    header-value  \0  5   \0  hello       \0
)

Same length-prefix framing as HMAC. The labels are literal strings content-type, header-name, header-value. The meta_sha256 is then fed into the HMAC computation as field #10.

You can verify it with sqlite3 and Python:

$ sqlite3 data/home%2Fnote/universe.db \
    "SELECT content_type, meta_sha256 FROM events WHERE id=2;"
text/plain|a1b2c3d4e5f6...

$ python3 -c "
import hashlib
def sha256_field(h, label, value):
    encoded = value.encode('utf-8')
    h.update(label); h.update(b'\0')
    h.update(str(len(encoded)).encode('ascii')); h.update(b'\0')
    h.update(encoded); h.update(b'\0')

h = hashlib.sha256()
sha256_field(h, b'content-type', 'text/plain')
# add header-name/header-value pairs here if any
print(h.hexdigest())
"

6. CAS (content-addressable storage)

Current bytes live inline in stage_meta.body for fast current reads. Timeline-addressed body copies live in cas_bodies, addressed by their SHA-256 hash. The cas_bodies table uses INSERT OR IGNORE: if two audit rows refer to the same historical body, only one CAS copy is stored.

-- Write path (inside one SQLite transaction):
UPDATE stage_meta
   SET body=?1, content_type=?2
 WHERE id=1;

DELETE FROM meta_headers;
INSERT INTO meta_headers(name, value)
    VALUES(...);

INSERT OR IGNORE INTO cas_bodies(body_sha256, body)
    VALUES(?3, ?1);

INSERT INTO events(timestamp, event_type, target,
    body_sha256, size, content_type, meta_sha256, hmac, prev_hmac)
    VALUES(...);

The events table references cas_bodies by hash. Multiple events can point to the same body (dedup). Retention prunes cas_bodies rows whose hash is no longer referenced by any event within the retention window. Chain rows (events) are never deleted.

-- Verify CAS integrity: actual hash must match stored hash
sqlite> SELECT body_sha256,
        hex(substr(body,1,8)),
        CASE WHEN body_sha256 = lower(hex(sha256(body)))
             THEN 'OK' ELSE 'TAMPERED' END as status
   FROM cas_bodies;

Note: SQLite does not have a built-in sha256() function. Use the Python verifier (tools/audit_chain_verify.py) or load an extension. The point is that the hash is deterministic and verifiable outside the engine.

Retention

cas_state.first_retained_seq tracks the retention floor. Bodies referenced only by events before this seq are eligible for pruning. On each durable write, the engine computes the new floor from the configured retained body count, deletes CAS rows that are referenced only before that floor, and then advances cas_state in the same SQLite transaction.

Chain rows are permanent. You can always walk the chain and see that event #3 wrote a body with hash e600da3b..., even if the body bytes have been pruned. The chain records what happened; CAS stores what it was. Pruning CAS does not break the chain.

7. Generation lifecycle

A generation is a 32-character lowercase hex string minted when a world is first created. It is stored in stage_meta.generation and signed into every event HMAC. The generation uniquely identifies one incarnation of a world.

# Create a world (first PUT auto-creates it)
$ curl -X PUT -H "Authorization: Bearer $TOKEN" \
    -d "first version" http://localhost:3105/home/note
201 Created

$ sqlite3 data/home%2Fnote/universe.db \
    "SELECT generation FROM stage_meta;"
a3f7c2e1b9d04856a3f7c2e1b9d04856

# Delete it
$ curl -X DELETE -H "Authorization: Bearer $APPROVE_TOKEN" \
    http://localhost:3105/home/note
204 No Content

# Re-create (PUT to a deleted world = new world)
$ curl -X PUT -H "Authorization: Bearer $TOKEN" \
    -d "phoenix" http://localhost:3105/home/note
201 Created

$ sqlite3 data/home%2Fnote/universe.db \
    "SELECT generation FROM stage_meta;"
5b2c7ed2f1a093475b2c7ed2f1a09347   ← different

Old timeline coordinates that reference the previous generation return 409 Conflict, not 404. The world exists, but it is not the same world. Clients holding stale cursors detect this and reset.

Generation entropy: 16 bytes from getrandom, rendered as 32 lowercase hexadecimal characters. Collision probability is negligible for any practical workload.

8. Timeline reads

Every body-bearing event produces a timeline address: the coordinates needed to read that exact historical body later. The address has four parts:

ParameterSource
timeline-seqevents.id (TimelineSeq)
timeline-generationstage_meta.generation (signed into the event HMAC)
timeline-body-sha256events.body_sha256 (64 hex)
timeline-worldworld path

Durable body-bearing events carry these coordinates. To read the historical body:

# Read current value
$ curl http://localhost:3105/home/note
version 10

# Read the body that was written at event seq=2
$ curl "http://localhost:3105/home/note?timeline=1\
&timeline-generation=a3f7c2e1b9d04856a3f7c2e1b9d04856\
&timeline-seq=2\
&timeline-body-sha256=ac1b5c0961a7269bf4ed..."
version 1

# Response headers include proof:
x-timeline-hmac: 739117dead6c29a1...
x-timeline-seq: 2
x-timeline-generation: a3f7c2e1b9d04856...

All four coordinates must match. If any one is wrong:

ConditionResponse
Wrong generation409 Conflict
Wrong body_sha256409 Conflict
seq out of range404 Not Found
seq points to non-body event (format)404 Not Found
Body pruned by retention410 Gone with timeline proof headers
seq=0 or negative400 Bad Request

The timeline address is not a subscription cursor. The SSE id (world@generation=seq) is for reconnection. The world component keeps / path separators and percent-escapes spaces or other non-canonical id bytes. The timeline address is for reading the exact body that was written at that point in history.

9. Two coordinate systems

There are two different sequence numbers. Confusing them is a bug.

TimelineSeqChainSeq
WhatSQLite rowid (events.id)Verified audit-chain ordinal
MeaningStorage coordinate for timeline reads and SSE idsProof coordinate minted by verifier walk
SourceSQLite AUTOINCREMENTVerifier walk from row 1
Used inTimeline reads, SSE idsChainStamp, witness judgments
Type in RustTimelineSeqChainSeq (NonZeroI64)
-- Normal intact chain: the values usually match, but they prove
-- different things. TimelineSeq names a row; ChainSeq names a verified step.
events.id | event_type | ChainSeq (not stored, computed by verifier)
----------+------------+---------
    1     | format     |    1
    2     | put        |    2
    3     | put        |    3
    4     | append     |    4

ChainStamp

A ChainStamp is a proof of position in the verified chain. It is only minted by the verifier after walking the chain from the beginning. It cannot be constructed from outside.

ChainStamp {
    generation: "0a1b2c3d...ef",   // which incarnation
    seq:        ChainSeq(5),        // verified step #5
    hmac:       "hmac-d4e9...a1",   // HMAC at that step
}

# Query chain head (latest verified position)
$ curl -I http://localhost:3105/proc/audit/home/note/head

# Query chain stamp at ordinal 3
$ curl -I http://localhost:3105/proc/audit/home/note/stamp/3

10. Append verification

Before every durable write, the engine verifies the existing chain inside the same SQLite transaction. The append sink requires a VerifiedAuditTx; code that has not proven the chain intact cannot append a new audit row.

-- Pseudocode of write path:
1. Acquire per-world write lock
2. Open a SQLite transaction
3. Verify the existing audit chain and live-body invariants
4. Mint VerifiedAuditTx                    -- proof token
5. Compute new HMAC with prev = last hmac
6. INSERT into events + cas_bodies
7. Commit
8. Notify subscribers

VerifiedAuditTx carries the checked transaction; append helpers require it. Full audit verification and append verification use the same signed rows and generation value.

12. Delete — two-phase with ledger

Delete is the most complex verb. It writes to two worlds in one operation:

1. Acquire target world lock (home/note)
2. Append delete_intent to ledger     ← "I intend to delete home/note"
3. Install tombstone and drain read-cache fds
4. Physically delete the target world directory
5. Clear tombstone, success or failure
6. If physical delete failed: return 500, with no delete_commit_failed row
7. Notify subject-world subscribers that the world is gone
8. Append delete_commit to ledger      ← "home/note is gone"
9. If commit append fails after physical delete:
     Append delete_commit_failed       ← "world is gone; normal commit append failed"

The delete ledger (var/log/deletes) is a regular world with its own HMAC chain. Its events carry proof headers identifying the deleted target:

HeaderValue
auditedb-delete-subject-worldtarget world path
auditedb-delete-subject-generation32 hex of deleted incarnation
auditedb-delete-subject-seqtimeline seq (positive i64)
auditedb-delete-subject-body-sha25664 hex
auditedb-delete-subject-hmachmac-<64hex>
# Inspect the delete ledger
$ sqlite3 data/var%2Flog%2Fdeletes/universe.db \
    "SELECT id, event_type, target FROM events ORDER BY id;"
1|format|var/log/deletes
2|delete_intent|home/note
3|delete_commit|home/note

Consequence: if the chain is tampered, delete also fails (because appending to the ledger requires a valid chain). An attacker who corrupts data cannot then delete it through the API to cover their tracks. The corrupted world is frozen.

$ curl -N -H "Authorization: Bearer $READ" \
    http://localhost:3105/listen/home/*

data: timeline-seq: 2

data: body-sha256: ac1b5c0961a7269b...
data: size: 11
data: content-type: text/plain

The SSE id is a durable subscription cursor: world@generation=timeline_seq. On reconnect, pass Last-Event-ID to resume from where you left off. Exact durable world subscriptions replay from that world's audit timeline. Wildcard subscriptions can only replay from the current process's bounded live ring; if the marker has fallen out, the stream reports reset with ring-miss.

Event kindHas idReplayable
put, append, formatyesyes
delete (on ledger world)yesyes
delete ping (on subject world)nono (live-only)
reset (generation changed, lagged)nono

Subscriptions do not carry body bytes. The event includes a timeline address; use a timeline read to fetch the actual body. This prevents large bodies from flooding the SSE stream.

At the Engine layer, subscription open and receive are both async: subscribe(...).await opens the stream and recv().await consumes it. The SSE adapter maps that Engine stream directly onto the HTTP event stream.

14. Four trust tiers

TierToken env varCan do
anon(none)nothing
readAUDITEDB_READ_TOKENread, subscribe, introspect
writeAUDITEDB_WRITE_TOKENread + replace, append
approveAUDITEDB_APPROVE_TOKENread + write + delete
# No token → 401
$ curl -X PUT -d "test" http://localhost:3105/home/note
401 Unauthorized

# Read token → can read, cannot write
$ curl -H "Authorization: Bearer $READ" http://localhost:3105/home/note
200 OK

# Write token → cannot delete
$ curl -X DELETE -H "Authorization: Bearer $WRITE" http://localhost:3105/home/note
401 Unauthorized

Tokens are compared in constant time. The HMAC key (AUDITEDB_KEY) is separate from auth tokens and never leaves memory. On process exit, the key is overwritten with zeros (volatile wipe).

15. Path validation

World paths are validated at the routing layer before reaching the engine. Invalid paths return 400 Bad Request, not storage errors.

RuleExample rejected
Must start with a known namespacefoo/bar
No backslasheshome/a\b
No empty segmentshome//note
No dot segmentshome/../etc/passwd
No percent-encoded dot segmentshome/%2e%2e/secret
No control charactershome/a\x00b
No bare namespace rootshome (need home/x)
No reserved pathsproc/version
Encoded disk name ≤ 200 byteshome/aaa...aaa (195 a's)

The 200-byte limit applies to the percent-encoded directory name, not the visible string length. A path with slashes, spaces, or non-ASCII characters will be percent-encoded on disk, and each encoded byte counts as 3. This prevents filesystem errors (ext4: 255-byte component limit) from becoming storage-layer 500 errors.

16. Tamper detection

If someone modifies the SQLite file outside the engine (e.g. with sqlite3 directly), the engine detects it and locks down:

What was tamperedDetectionEngine behavior
CAS body bytesSHA-256 mismatch on timeline read500 "timeline storage failure"
HMAC valuenext row's prev_hmac doesn't match500 on write (append verification fails)
Any events fieldHMAC recomputation fails500 on verify
Deleted a rowprev_hmac gapchain broken on verify
Inserted a rowHMAC doesn't match expected prevchain broken on verify
# Tamper a CAS body
$ sqlite3 data/home%2Fnote/universe.db \
    "UPDATE cas_bodies SET body=x'48414348454421' WHERE rowid=1;"

# Attempt to write → engine detects broken chain
$ curl -X PUT -H "Authorization: Bearer $WRITE" \
    -d "test" http://localhost:3105/home/note
500 Internal Server Error
internal error: storage failure

# Attempt to read → also rejected
$ curl http://localhost:3105/home/note
500 Internal Server Error

# Attempt to delete → also rejected (can't append to broken chain)
$ curl -X DELETE -H "Authorization: Bearer $APPROVE" \
    http://localhost:3105/home/note
500 Internal Server Error

After tampering, the world is frozen: no reads, writes, or deletes. The corrupted file is preserved for forensic investigation. Recovery requires manual removal of the SQLite file and re-creation of the world (which gets a new generation).

Forging a valid chain requires the HMAC key. The key is in memory only (environment variable), never written to disk.

17. Security boundary

The engine protects against API-layer attacks. It does not protect against OS-layer attacks. This is the same boundary as any database.

LayerWhat it providesWhat it cannot prevent
Engine (L5)HMAC chain, CAS integrity, auth tiers, path validationrm -rf, disk replacement, memory inspection
SQLiteACID transactions, crash recoveryfile deletion, external modification
Filesystempermissions (chmod 600)root access
OS kernelprocess isolationphysical access to hardware
# This is detected and blocked (API layer):
$ sqlite3 data/home%2Fnote/universe.db "UPDATE events SET hmac='fake';"
$ curl http://localhost:3105/home/note   → 500

# This is NOT detected (OS layer):
$ rm -rf data/home%2Fnote/
# world is gone. delete ledger has no record.
# re-creating via PUT will produce a new generation.

Known attack vectors

18. Format v2 marker

CREATE TABLE world_format(
    id      INTEGER PRIMARY KEY CHECK(id=1),
    version INTEGER NOT NULL CHECK(typeof(version)='integer') CHECK(version=2)
);
INSERT INTO world_format(id, version) VALUES(1, 2);

The marker is required. Old binaries fail on world_schema::verify() because the table is missing. New binaries reject v1 databases because world_format does not exist.

20. On-disk layout

data/                                ← data root (AUDITEDB_DATA or ./data)
  home%2Fnote/                       ← world "home/note" (percent-encoded)
    universe.db                      ← SQLite: events + cas_bodies + stage_meta + ...
  home%2Ftask%2F123/                 ← world "home/task/123"
    universe.db
  var%2Flog%2Fdeletes/               ← delete ledger (engine-private)
    universe.db
  .auditedb-writer-lock.sqlite3      ← single-writer SQLite lock (local FS only)

Each world is one directory with one SQLite file. cp -r data/home%2Fnote/ backup/ is a valid backup of that world. The directory name is the world path with /, %, ., spaces, non-ASCII bytes, and filesystem-sensitive characters percent-encoded. Control characters, backslashes, empty segments, and dot segments are rejected before the path reaches disk. The engine rejects paths whose encoded name exceeds 200 bytes.

.auditedb-writer-lock.sqlite3 is a SQLite database held open with an uncommitted BEGIN IMMEDIATE transaction. It ensures single-writer semantics within one host. It does not protect against NFS; network-FS deployments need external fencing.
